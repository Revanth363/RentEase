\section{Project Title and Description}

\subsection*{Title}
\begin{tcolorbox}[enhanced, colback=ctxBlue!30!white, colframe=primary,
  arc=4pt, boxrule=1pt, left=10pt, right=10pt, top=8pt, bottom=8pt]
  {\large\bfseries\color{primary} Tail Treasures: A Multi-Role Pet Care and Adoption Platform}
\end{tcolorbox}

\subsection*{Description}

\textbf{Tail Treasures} is a comprehensive, cloud-ready MERN-stack web application designed to unify the fragmented ecosystem of pet care services into a single, cohesive digital platform. Built with Node.js and Express for the backend, React with Redux for the frontend, and MongoDB as the primary data store, the platform addresses the end-to-end lifecycle of responsible pet ownership.

The platform serves \textbf{six distinct user roles}: customers who browse and adopt pets or purchase supplies, \textbf{sellers} who list and manage pet products, \textbf{veterinarians} who offer consultation services, \textbf{organisations (shelters)} that manage adoptable animals, and \textbf{administrators} (including co-admins) who govern the entire platform. Role-based access control enforced through JWT authentication and an approval workflow ensures that sellers, vets, and organisations are verified before gaining elevated access.

Core features include a \textbf{pet adoption pipeline} with scored applications, a \textbf{veterinary appointment scheduler} with real-time slot availability and geospatial vet discovery (using OpenStreetMap and OSRM), a full-featured \textbf{e-commerce engine} with cart management, GST-inclusive pricing, and order tracking, and a \textbf{financial ledger system} that records every transaction, calculates commissions, and supports admin-initiated payouts.

Supporting services include Redis-based caching, Cloudinary CDN integration for media uploads, an in-app notification system, a support messaging module, and role-specific dashboards with revenue analytics. The platform is documented with Swagger and tested using Jest and Supertest.

\textbf{Total models:} 12 | \textbf{API routes:} 60+ | \textbf{Frontend pages:} 30+

\section{Domain-Driven Design}

\subsection{Bounded Contexts}
%%─────────────────────────────────────────────────────────────

A \textbf{Bounded Context} is an explicit boundary within which a particular domain model applies and a consistent \textit{Ubiquitous Language} is maintained. For Tail Treasures, the domain is divided into \textbf{seven bounded contexts}, each owning its own model, data, and language. No two contexts share a database collection directly; cross-context communication occurs through well-defined interfaces.

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{bounded_context.png}
  \caption{Bounded Context Diagram — Tail Treasures Platform}
\end{figure}

\vspace{0.5em}

\begin{contextbox}{ctxBlue!80!black}{BC-1 \quad Identity \& Access Management Context}
\textbf{Purpose:} Manages all user identity, authentication, and authorisation concerns. Acts as the upstream provider for every other context — it owns the \texttt{User} entity and is the single source of truth for who is authenticated and what role they hold.

\textbf{Ubiquitous Language:} \textit{User, Role, Credential, Token, Approval, isApproved, isAdmin, Seller, Veterinary, Organisation, Customer, Co-Admin, Balance, ProfileImage, JWT, Google OAuth}

\textbf{Responsibilities:}
\begin{itemize}
  \item Local email/password registration and login
  \item Google OAuth 2.0 via Passport.js
  \item JWT issuance and validation
  \item Role-based access control (RBAC) enforcement
  \item Admin approval workflow for Sellers, Vets, and Organisations
  \item Profile management and password change
  \item Financial balance field on User (for seller/vet payouts)
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxGreen!80!black}{BC-2 \quad Pet Adoption Context}
\textbf{Purpose:} Owns the entire lifecycle of an adoptable animal, from intake by a shelter/organisation to final adoption. Manages the pet profiles and the multi-stage adoption application pipeline.

\textbf{Ubiquitous Language:} \textit{Pet, AdoptionApplication, Shelter, Species, Breed, HealthInfo, VaccinationStatus, AdoptionStatus, ApplicationScore, Applicant, ApprovalDecision, FeaturedPet}

\textbf{Responsibilities:}
\begin{itemize}
  \item CRUD for pet profiles with image uploads (Cloudinary/local)
  \item Pet status management: \texttt{available, pending, adopted, not\_available}
  \item Adoption application submission by customers
  \item Application scoring (scored model with home environment, experience, references)
  \item Application status workflow: \texttt{pending → under\_review → approved / rejected}
  \item Prevention of pet deletion when active applications exist
  \item Featured pet listings; breed/species filtering and text search
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxTeal!80!black}{BC-3 \quad Veterinary Care Context}
\textbf{Purpose:} Manages the full appointment scheduling lifecycle between customers and approved veterinarians, including geospatial discovery and slot-based availability.

\textbf{Ubiquitous Language:} \textit{Appointment, Veterinarian, TimeSlot, ConsultationFee, ServiceType, AvailableDays, ClinicAddress, GeoCoordinates, SlotAvailability, Booking, VetDashboard}

\textbf{Responsibilities:}
\begin{itemize}
  \item Real-time available time slot computation per vet per date
  \item Clash detection for double-booking prevention
  \item Appointment status workflow: \texttt{pending → confirmed → in-progress → completed / cancelled / no-show}
  \item Revenue recording on appointment completion (vet commission, balance credit)
  \item Geospatial vet discovery using MongoDB \texttt{2dsphere} index
  \item OSRM-based driving distance + Haversine fallback
  \item Vet clinic address and coordinates management via Nominatim geocoding
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxOrange!80!black}{BC-4 \quad E-Commerce Context}
\textbf{Purpose:} Handles the complete product commerce flow — from product listing by sellers to cart management, checkout, and order fulfilment.

\textbf{Ubiquitous Language:} \textit{Product, Category, Stock, SalePrice, Cart, CartItem, Order, OrderItem, ShippingAddress, PaymentMethod, OrderStatus, PaymentStatus, Review, Rating, PromoCode, Shipping}

\textbf{Responsibilities:}
\begin{itemize}
  \item Seller product CRUD with Cloudinary image support
  \item Real-time stock management and low-stock tracking
  \item Cart with 18\% GST calculation; free shipping above ₹1,000
  \item Cart validation: out-of-stock removal, quantity adjustment, price sync
  \item Order creation from cart; order number generation
  \item Order status: \texttt{pending → processing → shipped → delivered / cancelled}
  \item Stock restoration on cancellation; stock decrement on order creation
  \item Review submission with purchase verification; aggregate average rating
  \item Promo code application with min-order constraints
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxPurple!80!black}{BC-5 \quad Financial \& Revenue Context}
\textbf{Purpose:} Acts as the platform's financial ledger. Records every monetary event, aggregates daily/weekly/monthly revenue summaries, tracks seller/vet commissions, and processes admin payouts.

\textbf{Ubiquitous Language:} \textit{Transaction, Revenue, Payout, Commission, GrossRevenue, NetAmount, Tax, GST, PeriodIdentifier, SellerMetric, VetMetric, Balance, Ledger, Refund, Chargeback}

\textbf{Responsibilities:}
\begin{itemize}
  \item Ledger-based \texttt{Transaction} records for every sale, refund, commission, payout
  \item Daily \texttt{Revenue} aggregation records (periodType: daily)
  \item Per-seller commission calculation (default 10\%, configurable)
  \item Per-vet commission calculation on appointment completion
  \item Seller balance credit on order delivery; debit on cancellation/refund
  \item Admin payout processing with MongoDB session (atomic transaction)
  \item Revenue summary API for admin dashboard analytics
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxPink!80!black}{BC-6 \quad Communication Context}
\textbf{Purpose:} Manages all platform communication channels — support messages sent by users and in-app notifications delivered to users by system events.

\textbf{Ubiquitous Language:} \textit{Message, Notification, Recipient, IsRead, NotificationType, RelatedModel, SupportTicket, AdminReply, ClearAll, UnreadCount, TTL}

\textbf{Responsibilities:}
\begin{itemize}
  \item User support message submission and admin reply system
  \item Message read/unread status management by admin
  \item In-app notification creation (called by other contexts via \texttt{createNotification})
  \item Notification read/unread/clear-all operations per user
  \item Auto-expiry of notifications after 30 days (MongoDB TTL index)
  \item Notification count badge for navbar UI
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxRed!80!black}{BC-7 \quad Platform Administration Context}
\textbf{Purpose:} Provides administrative governance across the entire platform. Manages user approvals, content moderation, co-admin provisioning, and platform-wide analytics.

\textbf{Ubiquitous Language:} \textit{Admin, CoAdmin, Approval, UserManagement, PlatformStats, ContentModeration, PendingApproval, RolePromotion, DashboardSummary}

\textbf{Responsibilities:}
\begin{itemize}
  \item Approve/reject sellers, vets, and organisations
  \item Update or delete any user, order, pet, product, or application
  \item Co-admin provisioning (create, list, delete co-admins)
  \item Access to all financial reports and ledger data
  \item Initiate payouts to sellers/vets
  \item Admin dashboard with cross-context aggregated statistics
  \item Role-switching between Admin and Co-Admin dashboards
\end{itemize}
\end{contextbox}

\subsection{Context Mappings}
%%─────────────────────────────────────────────────────────────

Context Mapping defines how bounded contexts relate to and integrate with each other, describing the \textit{direction of influence} (upstream/downstream) and the \textit{integration pattern} used. In DDD, \textbf{[U]} denotes the upstream context (supplier) and \textbf{[D]} denotes the downstream context (consumer).

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{context_mapping.png}
  \caption{Context Mapping Diagram — Integration Patterns between Bounded Contexts}
\end{figure}

\subsubsection*{Integration Pattern Legend}

\begin{center}
\begin{tabular}{@{}lp{10cm}@{}}
\toprule
\textbf{Pattern} & \textbf{Description} \\
\midrule
\textbf{OHS} — Open Host Service & Upstream publishes a well-defined, stable API consumed by many downstream contexts. \\
\textbf{PL} — Published Language & Structured data format (e.g., JWT payload, JSON schema) shared as a contract. \\
\textbf{C/S} — Customer / Supplier & Asymmetric relationship; supplier (U) provides, customer (D) consumes and can negotiate. \\
\textbf{CF} — Conformist & Downstream adopts upstream model with no translation layer; accepts upstream as-is. \\
\textbf{ACL} — Anti-Corruption Layer & Downstream creates a translation layer to shield its model from the upstream. \\
\textbf{ED} — Event-Driven & Loosely coupled, one-way notification; upstream fires an event, downstream reacts. \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Entities, Value Objects, and Domain Services per Subdomain}

\subsection{Aggregates}
%%─────────────────────────────────────────────────────────────

An \textbf{Aggregate} is a cluster of domain objects (entities and value objects) treated as a single unit for data changes. Each aggregate has exactly one \textbf{Aggregate Root} — the only object through which external actors interact with the cluster. All invariants within the aggregate are enforced by the root.

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{aggregates.png}
  \caption{Aggregate Diagram — Aggregate Roots, Entities, and Value Objects}
\end{figure}

\subsubsection{AG-1: User Aggregate}

\begin{infobox}{Aggregate Root: \texttt{User}}
\begin{tabular}{@{}p{3cm}p{2.8cm}p{7.8cm}@{}}
\textbf{Component} & \textbf{Type} & \textbf{Notes} \\
\hline
User & \textbf{Aggregate Root} & Global identity; all cross-context references point to User.\_id \\
SellerInfo & Value Object & Embedded subdocument; mutated only through User.save() \\
VetInfo & Value Object & Contains GeoJSON coordinates; updated via User.findByIdAndUpdate \\
Address & Value Object & Embedded; user's contact/delivery address \\
Balance & Value Object & Scalar field on User; modified atomically in Financial context \\
\end{tabular}

\textbf{Invariants:} Password must be bcrypt-hashed before save (pre-save hook). If role is seller/vet/org, isApproved must be true before login is permitted. Balance cannot go negative (enforced in PayoutService).
\end{infobox}

\subsubsection{AG-2: Pet Aggregate}
