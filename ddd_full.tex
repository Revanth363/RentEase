\subsection*{Title}
\begin{tcolorbox}[enhanced, colback=ctxBlue!30!white, colframe=primary,
  arc=4pt, boxrule=1pt, left=10pt, right=10pt, top=8pt, bottom=8pt]
  {\large\bfseries\color{primary} RentEase: A Home Rental Management Platform}

\subsection*{Description}

\textbf{RentEase} is a comprehensive rental management platform that connects property owners, tenants, and domestic workers in one place. Owners can list their properties---whether apartments, houses, or commercial spaces---with complete details such as location, price, number of bedrooms and bathrooms, and furnishing status. Each owner has a dedicated dashboard to track rental income, view commission breakdowns, monitor bookings, and handle maintenance requests.

Tenants can search and browse available properties, submit booking requests, and pay rent securely through Razorpay integration. The payment system records every transaction and shows the platform commission alongside the net amount transferred to the owner. Tenants can also rate and review properties to help other users make informed decisions, and they manage all their bookings and domestic worker hirings from their own dashboard.

Workers register on the platform and use their dashboard to manage service bookings, track earnings, and view detailed payment histories---all processed through the same Razorpay gateway for full transparency.

The platform uses a multi-level administration system. Regular admins manage user verifications, bookings, maintenance requests, and payments. Superadmins handle financial analytics, owner and worker earnings reports, executive management, audit logs, and system-wide configuration.

A KYC verification system ensures that all users and properties are legitimate before they can access platform features. The system is secured with JWT authentication, structured error handling, and comprehensive logging throughout.

\textbf{Total models:} 23 | \textbf{API routes:} 12 route files | \textbf{Controllers:} 27

\section{Domain-Driven Design}

\subsection{Bounded Contexts}
%%─────────────────────────────────────────────────────────────

A \textbf{Bounded Context} is an explicit boundary within which a particular domain model applies and a consistent \textit{Ubiquitous Language} is maintained. RentEase is divided into \textbf{14 Bounded Contexts} grouped into four domain categories. No two contexts share a database collection directly; cross-context communication occurs through well-defined interfaces.

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{RentEase_DDD.png}
  \caption{Bounded Context Diagram — RentEase Platform}
\end{figure}

\vspace{0.5em}

%%── Core Domains ─────────────────────────────────────────────

\begin{contextbox}{ctxBlue!80!black}{BC-1 \quad Property Management Context}
\textbf{Purpose:} Manages the core property inventory and owner lifecycle. Property can only be rented if \texttt{isVerified=true}; only verified owners can list properties.

\textbf{Ubiquitous Language:} \textit{Property, Owner, Location, Amenity, PropertyImage, isVerified, isRented, FurnishingType, SecurityDeposit, LeaseDuration, ActiveWorkers, PropertyProof}

\textbf{Responsibilities:}
\begin{itemize}
  \item Property CRUD with Cloudinary image and proof uploads
  \item Property verification/rejection workflow by admin
  \item Owner registration, profile management, and earnings tracking
  \item Property search by location, type, price, furnishing
  \item Active worker pre-save validation (only valid workers attached)
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxGreen!80!black}{BC-2 \quad Tenant Management Context}
\textbf{Purpose:} Manages tenant registrations, profiles, and platform interactions. Tenant can only book if verified; cannot book the same property twice simultaneously.

\textbf{Ubiquitous Language:} \textit{Tenant, SavedListing, RentalHistory, NotificationPreferences, DomesticWorker, ContactInfo, AccountStatus}

\textbf{Responsibilities:}
\begin{itemize}
  \item Tenant registration, activation, and suspension
  \item Saved listings (bookmark properties)
  \item Rental history tracking (append-only per tenant)
  \item Notification preference management
  \item Domestic worker hiring from tenant dashboard
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxTeal!80!black}{BC-3 \quad Booking / Rental Lifecycle Context}
\textbf{Purpose:} Manages the entire rental process from request to active lease, including termination. State Machine: Pending $\rightarrow$ Approved $\rightarrow$ Active $\rightarrow$ Terminated | Rejected.

\textbf{Ubiquitous Language:} \textit{Booking, RentalAgreement, UnrentRequest, BookingStatus, LeaseDetails, AgreementTerms, StartDate, EndDate, AssignedWorker}

\textbf{Responsibilities:}
\begin{itemize}
  \item Booking creation, approval, rejection, and termination
  \item Rental agreement generation and signing
  \item Unrent (early termination) request handling
  \item Status transition enforcement via state machine
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxOrange!80!black}{BC-4 \quad Payment Processing \& Ledger Context}
\textbf{Purpose:} Handles all monetary transactions, commission tracking, and the financial ledger via Razorpay integration. Commission is calculated at payment time and is immutable.

\textbf{Ubiquitous Language:} \textit{Payment, Razorpay, OrderId, Commission, CommissionPercent, RefundId, RefundAmount, PaymentStatus, TransactionId, ReceiptUrl}

\textbf{Responsibilities:}
\begin{itemize}
  \item Razorpay order creation and payment verification
  \item Commission calculation and snapshot at payment time
  \item Refund processing with reason tracking
  \item Payment status management: Pending, Paid, Overdue, Refunded, Failed, Cancelled
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxPurple!80!black}{BC-5 \quad Worker Services Context}
\textbf{Purpose:} Manages domestic worker profiles, availability, and service offerings. Worker is visible only if verified; availability updates based on active bookings.

\textbf{Ubiquitous Language:} \textit{Worker, ServiceType, AvailabilityStatus, ServiceRate, WorkerProfile, RateUnit, Experience, IsBooked, ClientIds}

\textbf{Responsibilities:}
\begin{itemize}
  \item Worker registration, search by location/service type
  \item Availability status management (Available, Booked, OnLeave)
  \item Worker profile with Cloudinary image upload
  \item Client relationship tracking
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxPink!80!black}{BC-6 \quad Worker Booking \& Payments Context}
\textbf{Purpose:} Manages service bookings and a separate payment ledger for worker earnings. Payment amount = workingDays $\times$ dailyRate; commission immutable at payment time.

\textbf{Ubiquitous Language:} \textit{WorkerBooking, WorkerPayment, WorkTracking, OTP, WorkingDays, DailyRate, CommissionSnapshot, PreferredDate, ServiceType}

\textbf{Responsibilities:}
\begin{itemize}
  \item Worker service booking creation, approval, completion
  \item Worker payment with working days calculation
  \item Daily work attendance tracking via OTP verification
  \item Commission calculation and Razorpay processing
\end{itemize}
\end{contextbox}

\textbf{Ubiquitous Language:} \textit{MaintenanceRequest, Complaint, IssueType, TenantConfirmation, ScheduledDate, CompletionDate, Response}

\textbf{Responsibilities:}
\begin{itemize}
  \item Maintenance request creation, scheduling, and completion
  \item Tenant confirmation workflow (Pending, Confirmed, Rejected)

\vspace{0.5em}

\begin{contextbox}{ctxYellow!80!black}{BC-8 \quad Rating \& Review Context}

\textbf{Ubiquitous Language:} \textit{Rating, Review, RatingScore, RatingContext, VerifiedBooking, PropertyRating, WorkerRating}

\textbf{Responsibilities:}
\begin{itemize}
  \item Rating submission (1--5 scale) with review text
  \item Rating for properties, owners, and workers
  \item Average rating aggregation on target entities
\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxIndigo!80!black}{BC-9 \quad Verification / KYC Context}
\textbf{Purpose:} Verifies the identity of users before granting platform access. One verification record per user; access gated on \texttt{status=approved}. Uses polymorphic \texttt{refPath} discriminator.

\textbf{Ubiquitous Language:} \textit{Verification, Document, UserModel, RejectionReason, Reviewer, Aadhaar, PAN, DrivingLicense, SkillCertificate}

\textbf{Responsibilities:}
\begin{itemize}
  \item Document submission (aadhaar, pan, driving\_license, college\_id, skill\_certificate)

\end{itemize}
\end{contextbox}

\vspace{0.5em}

\begin{contextbox}{ctxLime!80!black}{BC-10 \quad Notification Context}

\textbf{Ubiquitous Language:} \textit{Notification, RecipientType, NotificationType, Priority, Read, IsNew, BookingId, PropertyName}

\textbf{Responsibilities:}

\subsection{Context Mappings}
%%─────────────────────────────────────────────────────────────

Context Mapping defines how bounded contexts relate to and integrate with each other, describing the \textit{direction of influence} (upstream/downstream) and the \textit{integration pattern} used. In DDD, \textbf{[U]} denotes the upstream context (supplier) and \textbf{[D]} denotes the downstream context (consumer).

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{context_mapping.png}
  \caption{Context Mapping Diagram — Integration Patterns between 14 Bounded Contexts}
\end{figure}

\subsubsection*{Integration Pattern Legend}

\begin{center}
\begin{tabular}{@{}lp{10cm}@{}}
\toprule
\textbf{Pattern} & \textbf{Description} \\
\midrule
\textbf{U/D} — Upstream/Downstream & One context depends on another; downstream consumes upstream's data. \\
\textbf{OHS} — Open Host Service & Upstream publishes a well-defined API consumed by many downstream contexts. \\
\textbf{C/S} — Customer / Supplier & Asymmetric relationship; supplier provides, customer consumes and can negotiate. \\
\textbf{CF} — Conformist & Downstream adopts upstream model with no translation; accepts as-is. \\
\textbf{SK} — Shared Kernel & Two contexts share a subset of the domain model (e.g., shared IDs). \\
\textbf{ACL} — Anti-Corruption Layer & Downstream creates a translation layer to shield its model from upstream. \\

\end{tabular}

\subsubsection*{Key Implementation Notes}

\begin{enumerate}
  \item \textbf{Polymorphic References:} Verification uses \texttt{user} + \texttt{userModel} enum; Notification uses \texttt{recipient} + \texttt{recipientType} enum.
  \item \textbf{Many-to-Many:} Stored as arrays of ObjectIds: \texttt{owner.propertyIds}, \texttt{tenant.savedListings}, \texttt{property.activeWorkers}.
  \item \textbf{Constraints in Code:} 1:0..1 Tenancy via \texttt{property.isRented} boolean; 1:1 Verification per user; 1:1 RentalHistory per tenant (append-only).
  \item \textbf{Referential Integrity:} MongoDB has no cascade deletes. Soft deletes (\texttt{isDeleted} flag) recommended to prevent orphaned records.
\end{enumerate}

\subsubsection*{Aggregate Design Patterns}

\begin{enumerate}
  \item \textbf{Polymorphic Aggregates} — Verification and Notification use a \texttt{refPath} discriminator to serve multiple user types.
  \item \textbf{Immutable Value Objects} — RazorpaySignature and commission percentage are captured at payment time and never changed.
  \item \textbf{State Machines} — Booking, WorkerBooking, and Verification follow strict state transition rules.
  \item \textbf{Verification Gates} — Tenant, Owner, and Worker must have an approved Verification before accessing key features.
  \item \textbf{Denormalisation} — Arrays of ObjectIds for query optimisation, trading consistency for read performance.
\end{enumerate}
